# 任务（Task）执行方案

> 本文档只规划设计，不包含任何代码。覆盖 `Task / TaskItem / TaskItemData` 三张表从创建到完成的完整生命周期。

---

## 1. 总体架构

```
                                ┌────────────────────────────────────────────┐
                                │           APScheduler (进程内)              │
                                │   - 启动时从 DB 加载 active=True 的 task     │
                                │   - 每个 task 注册一个 IntervalTrigger       │
                                │   - 任务变更时动态 add/remove job            │
                                └────────────────┬───────────────────────────┘
                                                 │ trigger
                                                 ▼
                              ┌──────────────────────────────────┐
                              │  TaskRunner.run(task_id)         │
                              │  全异步 (asyncio + httpx)         │
                              │  CPU 密集 → run_in_executor       │
                              └──────────────────────────────────┘
                                                 │
            ┌──────────────┬──────────────┬──────┴───────┬──────────────┬──────────────┐
            ▼              ▼              ▼              ▼              ▼              ▼
        Step1 拉取     Step2 下载       Step3 详情       Step4 LLM      Step5 匹配     Step6 上传
        TaskItem      文件             TaskItemData    识别           判定           训练目录
```

### 1.1 模块划分（建议新增）

| 路径 | 职责 |
|---|---|
| `services/task.py` | 任务 CRUD：create / list / detail / update / delete / toggle_active |
| `services/task_runner.py` | 执行链编排：`run_task(task_id)` 总入口，串联 6 个 Step |
| `services/task_steps/fetch.py` | Step1：拉取 TaskItem |
| `services/task_steps/download.py` | Step2：下载文件 |
| `services/task_steps/detail.py` | Step3：拉取 TaskItemData |
| `services/task_steps/llm.py` | Step4：调用大模型识别 |
| `services/task_steps/matcher.py` | Step5：bbox / track_id 匹配判定 |
| `services/task_steps/uploader.py` | Step6：远端提交 + 训练目录 |
| `services/task_scheduler.py` | APScheduler 封装，监听 task 变更 |
| `services/upstream_api.py` | 统一封装 3 个上游业务接口（分页查询、文件详情、更新结果） |
| `api/task.py` | 路由层 |
| `schemas/task.py` | 请求/响应模型 |

### 1.2 上游接口对照表

| 名称 | 用途 | 调用时机 |
|---|---|---|
| 分页查询影像数据 2.0 | 根据筛选条件拉取符合的影像列表 | Step1 |
| 根据 fileId 获取影音文件详情 1.0 | 拉取单个文件的识别结果详情 | Step3 |
| 更新 ai 巡检结果 | 把 LLM 修正后的结果回写 | Step6 |

> 三者均通过现有 `services/client_auth.perform_authenticated_request` 调用，自动处理 token 刷新。

## 2. 任务创建（Step 0）

### 2.1 创建参数

| 字段 | 来源 | 说明 |
|---|---|---|
| name | 用户输入 | 任务名称 |
| client_id | 选择项目 | 关联 `client.id` |
| config_id | 选择提示词 | 关联 `config.id` |
| interval | 单选 | 1/6/12/24/168 小时 |
| filters | 复合表单 | 见 2.2 |
| execution_mode | 自动 / 手动 | 决定是否进入 LLM、上传步骤 |
| auto_confirm | 自动模式专属 | 是否跳过人工确认直接上传 |

### 2.2 筛选条件 (`filters_json`)

序列化为 JSON 存进 `task.filters_json`，结构：

```
{
  "classify": [int],        // 识别分类
  "keyword":  str,          // 关键词
  "spName":   [str],        // 物种名称
  "fileBmp":  [int],        // 文件格式 (1=图片, 2=视频)
  "idType":   [int],        // 识别类型
  "uploadType": [int],      // 上传类型
  "startTime": "YYYY-MM-DD HH:MM:SS",
  "endTime":   "YYYY-MM-DD HH:MM:SS"
}
```

> Step1 调用上游分页接口时把 `filters_json` 反序列化后填入请求体。`startTime / endTime` 不直接发给上游，而是与「滚动窗口」机制（见第 2.4 节）合并后再发。

### 2.3 创建后动作

1. 写入 `task` 表，`execution_status=CREATE`，`active` 默认为 `false`。
2. 用户点击「启用」→ `active=true` → 调度器注册 job。
3. 用户点击「立即执行」→ 直接异步触发一次 `run_task(task_id)`，不依赖间隔。

### 2.4 滚动时间窗口（自动模式专属）

为避免每次自动触发都拉到大量历史重复数据，task 维护两个独立时间游标：

| 字段（建议新增到 `task` 表） | 含义 |
|---|---|
| `last_pull_end_at` (datetime) | 上一次拉取数据时使用的结束时间（即数据时间上界） |
| `last_run_started_at` (datetime) | 上一次执行的发起时间（用于人工排查） |

**首次执行**（`last_pull_end_at IS NULL`）：
- 起始时间 = `filters_json.startTime`（用户填的初始下界）
- 结束时间 = `now()`

**后续执行**（`last_pull_end_at` 非空）：
- 起始时间 = `last_pull_end_at`（紧接上一次的上界，不留空隙）
- 结束时间 = `now()`

**特殊处理**：
- 若用户填了 `filters_json.endTime`，且当前 `now() > endTime`，结束时间统一截断到 `endTime`，意味着任务到期不再向后滚动
- 若 `endTime` 已过且 `last_pull_end_at >= endTime` → 直接跳过本次执行，并把 `task.active=false`（任务自然结束）

**写回时机**：Step1 拉取完成后立即把本次执行使用的结束时间写入 `last_pull_end_at`，无论后续 Step2~6 成功失败。这样即使下载/识别失败，下次也不会重复拉同一时间窗。

**手动模式**：不使用滚动窗口，每次都按 `filters_json` 原值拉取，由用户自行控制时间范围（手动场景下 file_fid 去重仍然兜底，见第 2.5 节）。

### 2.5 重复数据去重（双重防护）

滚动窗口能避免大部分重复，但仍有两种场景会拉到重复数据：
- 上游接口同一 file_fid 落在两次窗口的边界
- 用户手动调整过 `filters_json.startTime` 倒回了历史
- 手动模式没有滚动窗口

因此 Step1 必须做 **数据库层去重**：

**第一道：数据库唯一约束**

```
task_item: 复合唯一索引 (task_id, file_fid)
```

**第二道：Step1 写库前查询**

```
拉到一批数据后:
  existing_fids = SELECT file_fid FROM task_item WHERE task_id=? AND file_fid IN (...)
  new_items = [item for item in batch if item.file_fid NOT IN existing_fids]
  bulk_insert(new_items)
  log.info("本批 {} 条, 已存在 {} 条, 新增 {} 条")
```

**判定原则**：以 `file_fid` 为业务唯一键。同一 fid 命中已存在记录 → 直接丢弃，不更新已有记录的任何字段（避免覆盖人工已确认的结果）。

**统计字段**：建议在 `task` 表加 `skipped_count` 字段，记录历次执行累计跳过的重复条数，便于运维观测窗口策略是否合适。

## 3. 任务执行链路

### 3.1 状态机（Task.execution_status）

```
CREATE ──触发──▶ DOWN ──成功──▶ LLM ──成功──▶ VERIFY ──成功──▶ SUBMIT ──成功──▶ FINISH
   │              │              │              │              │
   └──失败────────┴──失败────────┴──失败────────┴──失败────────┴──▶ FAIL
```

每一步开始时更新 `execution_status` 与 `started_at / updated_at`，结束时更新 `processed_count`。任意一步抛错 → `execution_status=FAIL` + `last_error=str(exc)`，并保留中间产物便于排查。

### 3.2 TaskItem 状态字段

| 字段 | 阶段 | 取值 |
|---|---|---|
| `down_state` (bool) + `down_error` | Step2 | False/True |
| `file_path` | Step2 | 本地保存路径 |
| `llm_state` (str) + `llm_error` + `llm_at` | Step4 | `pending/running/success/fail/skipped` |
| `confirm_state` + `confirmed_at` | Step5 | `pending/auto_confirmed/manual_confirmed/rejected` |
| `remote_state` + `remote_error` + `remote_at` | Step6 | `pending/success/fail` |
| `train_state` + `train_at` | Step6 | `pending/saved/fail` |
| `status` (流程总状态) | 所有 | `created/downloading/llm/verified/submitted/done/failed` |

### 3.3 TaskItemData 状态字段（已存在）

```
status ∈ {DEFAULT, ADD, UPDATE, DELETE}
```

- DEFAULT：原始识别结果，未变更
- ADD：LLM 检出但 resultFileData 没有 → 新增一行（仅图片）
- UPDATE：bbox 匹配成功但名称不同 → 更新该行的 `llm_name`
- DELETE：resultFileData 有但 LLM 没识别到 → 改该行 status

## 4. Step1 — 拉取 TaskItem

**输入**：`task.id` + `task.filters_json` + `task.client_id` + `task.last_pull_end_at`
**调用**：`分页查询影像数据 2.0`（分页循环直到取完）

**时间窗口处理**（自动模式）：
1. 计算本次 `[start, end]`：
   - `start = task.last_pull_end_at or filters_json.startTime`
   - `end   = min(now(), filters_json.endTime or now())`
2. 若 `start >= end` → 跳过本次执行，直接 FINISH 并保留 active 状态
3. 把 `start / end` 覆盖到上游请求的 `startTime / endTime` 字段

**写库**：批量写入 `task_item` 表，初始字段：
- `name / device_name / file_num / file_extension / file_url / file_fid`
- `sp_name_list / classify / file_bmp / id_type`
- `result_file_data`（视频时为 json 文件 url，图片可空）
- `status="created"`，`down_state=false`，`llm_state=null`

**去重**：以 `(task_id, file_fid)` 唯一约束 + 写库前 SELECT 过滤（详见第 2.5 节）。重复触发同任务时跳过已存在 item，**不覆盖已有数据**。

**收尾**：分页全部成功后，把本次的 `end` 写入 `task.last_pull_end_at`、跳过条数累加到 `task.skipped_count`。

**异常**：分页中途失败 → 已落库 item 保留，`task.execution_status=FAIL`，`last_pull_end_at` **不更新**（下次重新拉同一窗口）。

---

## 5. Step2 — 下载文件

**并发**：`asyncio.Semaphore(N)` 控制并发数（建议 N=8），httpx 异步下载。
**保存目录**（结合 `config.data_dir`）：

```
{data_dir}/task_files/{task_id}/{task_item_id}/
   ├── original.{ext}        # 图片或视频原文件
   └── result.json           # 视频专属：result_file_data 下载的 json
```

**流程**：
1. 下载 `file_url` → `original.{ext}`，写入 `file_path`
2. 若 `file_bmp=2`（视频）且 `result_file_data` 非空 → 下载 json 到 `result.json`
3. 成功：`down_state=true`；失败：`down_state=false`、`down_error=msg`，整个 task 不中断（继续处理其他 item，最后汇总失败数）

---

## 6. Step3 — 拉取 TaskItemData

**调用**：`根据 fileId 获取影音文件详情 1.0`，参数 `file_fid`
**写入**：上游返回的每条识别结果生成一行 `task_item_data`：

- `name / score / track_ids / sp_amount`
- `minx / miny / maxx / maxy`（bbox）
- `llm_name=null`（待 Step4 填）
- `status=DEFAULT`

> 视频的 track_ids 来自上游聚合结果，每行对应一个个体的全程轨迹。

---

## 7. Step4 — LLM 识别

**前置**：`execution_mode=AUTO` 才执行；MANUAL 模式跳过，等用户在前端逐条点「识别」。
**调用**：`services/multimodal_model.chat_with_multimodal_model`，model 由 task 配置或全局默认（建议在 task 上加 `model_id` 字段，下一版补）。
**Prompt**：从 `config_id` 读取 `Config.text`，要求模型严格输出 JSON：

```
{
  "objects": [
    {"name": "<物种名>", "bbox": [minx, miny, maxx, maxy], "track_id": <可选>}
  ]
}
```

### 7.1 图片分支 (`file_bmp=1`)

1. 直接把 `file_path` 整张图 base64 编码 → 作为 image attachment
2. 一次调用 → 一个 `objects[]` 数组
3. 把结果传给 Step5 的图片匹配器

### 7.2 视频分支 (`file_bmp=2`)

按 **track_id 分组 + 关键帧抽样** 策略：

1. 加载 `result.json`（每帧 detection），按 track_id 分组
2. 每个 track 选 **3 帧关键帧**：
   - 首帧、bbox 面积最大帧、末帧（去重后实际可能 1~3 帧）
3. 用 ffmpeg/opencv 抽出这些帧 → 临时图片
4. 按 track 把多张关键帧打成一个 LLM 请求（同一附件组）
5. LLM 回答该 track 的 `name` → 直接归到这个 `track_id` 上
6. 所有 track 处理完后产出 `objects[]`，每个对象带 `track_id`

> 抽帧、IoU 计算、ffmpeg 调用都是 CPU/IO 阻塞操作，统一放 `loop.run_in_executor(thread_pool, ...)`。

**写库**：识别完成后，先把每个 track / object 的 LLM 名称暂存内存，进入 Step5 后再决定如何反映到 `task_item_data`。
**状态**：`llm_state=success / fail`，`llm_at=now()`，失败原因存 `llm_error`。

---

## 8. Step5 — 匹配判定

### 8.1 图片匹配（IoU ≥ 0.5）

```
原始 = 该 task_item 下所有 task_item_data (status=DEFAULT)
LLM  = Step4 返回的 objects[]

for llm_obj in LLM:
    best = max(原始, key=lambda o: IoU(o.bbox, llm_obj.bbox))
    if best.IoU >= 0.5:
        if best.name == llm_obj.name:
            best.llm_name = llm_obj.name   # 一致, 仍 DEFAULT
        else:
            best.llm_name = llm_obj.name
            best.status   = UPDATE
        mark(best, matched)
    else:
        新增 task_item_data(
            bbox=llm_obj.bbox, llm_name=llm_obj.name,
            status=ADD, name=null, score=null
        )

for orig in 原始 if not matched:
    orig.status = DELETE
```

### 8.2 视频匹配（按 track_id 直接合并）

```
原始 = 该 task_item 下所有 task_item_data (一行 = 一个 track)
LLM  = {track_id: name}

for orig in 原始:
    llm_name = LLM.get(orig.track_id)
    if llm_name is None:
        orig.status = DELETE          # LLM 没识别到该 track
    elif llm_name == orig.name:
        orig.llm_name = llm_name      # 仍 DEFAULT
    else:
        orig.llm_name = llm_name
        orig.status   = UPDATE

# 视频不产生 ADD（按你的需求）
```

**确认状态**：
- `auto_confirm=true` → `task_item.confirm_state=auto_confirmed`，直接进入 Step6
- `auto_confirm=false` → `confirm_state=pending`，等待前端人工确认接口
- 手动模式 (`execution_mode=MANUAL`) → 跳过 Step5/6，由前端独立按钮触发

---

## 9. Step6 — 远端提交 + 训练目录

**触发条件**：仅对 `task_item_data.status ∈ {ADD, UPDATE, DELETE}` 的 item 执行（DEFAULT 跳过）。

### 9.1 远端提交

**调用**：`更新 ai 巡检结果`，按 `file_fid` 维度提交所有差异
**载荷**：构造 `{fileId, results: [...]}`，results 中：
- ADD/UPDATE：用 `llm_name + bbox`
- DELETE：标记移除原项

成功 → `remote_state=success`，`remote_at=now()`
失败 → `remote_state=fail`，`remote_error=msg`，**不阻断**训练目录保存

### 9.2 保存到训练目录

```
{data_dir}/training/{task_id}/{task_item_id}/
   ├── original.{ext}
   ├── annotation.json   # 包含原始标注 + LLM 标注 + 差异
   └── (视频额外) result.json
```

`train_state=saved` / `fail`，`train_at=now()`

### 9.3 自动 vs 手动

| 模式 | Step4 | Step5 | Step6 |
|---|---|---|---|
| AUTO + auto_confirm=true | 自动 | 自动 | 自动 |
| AUTO + auto_confirm=false | 自动 | 自动写状态 | 等人工确认接口 |
| MANUAL | 等用户点「识别」按钮 | 等用户点「确认」按钮 | 等用户点「提交」按钮 |

## 10. 调度器设计（APScheduler）

### 10.1 启动

`main.py` 的 `lifespan` 中：
1. 创建 `AsyncIOScheduler`
2. 查询 `task.active=True` 的全部任务
3. 为每个任务注册 `IntervalTrigger(hours=task.interval)`，job_id=`task_{id}`
4. 监听任务的 CRUD：
   - 新增 active 任务 → `add_job`
   - 关闭 active → `remove_job`
   - 修改 interval → `reschedule_job`

### 10.2 触发逻辑

```
async def run_task_job(task_id):
    if 该 task 仍在执行 (execution_status not in {FINISH, FAIL, CREATE}):
        skip + log warn       # 防重入
        return
    await TaskRunner(task_id).run()
```

### 10.3 防止僵尸任务

- 每次启动时，把 `execution_status` 卡在中间态超过 N 小时的 task 重置为 `FAIL`，附 `last_error="启动时检测到僵尸状态"`
- 单个 step 可加 `asyncio.timeout()` 兜底

## 11. API 路由（建议）

> 遵守项目规范：禁止空路径或纯动态参数路由。

| Method | Path | 说明 |
|---|---|---|
| GET | `/api/tasks/list` | 列表（分页+筛选） |
| GET | `/api/tasks/detail/{id}` | 任务详情 + 进度统计 |
| POST | `/api/tasks/create` | 创建 |
| POST | `/api/tasks/update/{id}` | 修改 |
| DELETE | `/api/tasks/delete/{id}` | 删除（级联） |
| POST | `/api/tasks/action-start/{id}` | 启用 active |
| POST | `/api/tasks/action-stop/{id}` | 停用 active |
| POST | `/api/tasks/action-run/{id}` | 立即执行一次 |
| GET | `/api/task-items/list` | TaskItem 列表 (`?task_id=&media_type=&page=&page_size=`) |
| GET | `/api/task-items/detail/{id}` | TaskItem 详情 + TaskItemData |
| POST | `/api/task-items/action-confirm` | 人工确认 |
| POST | `/api/task-items/action-reject` | 人工拒绝 |
| POST | `/api/task-items/action-delete` | 只删除复核层对象 / 待提交差异集合 |
| POST | `/api/task-items/action-submit` | 提交远端 + 训练目录 |

### 11.1 Review compat 精炼通道

`/api/reviews/*` 只保留为旧 `Review` 页面过渡适配层。它不得重新承载主业务规则，
也不得绕过 `Task / TaskItem / TaskItem Actions` canonical contract。

| Compat Path | Canonical 语义 |
|---|---|
| `GET /api/reviews/completed-tasks` | 从已结束 `Task` 与其 `TaskItem` 投影出旧任务下拉选项 |
| `GET /api/reviews?taskId=...` | 从 `TaskItem + TaskItemData` 投影旧复核卡片与 `reviewRows` |
| `POST /api/reviews/confirm` | 委托 `TaskItem action-confirm`，只更新确认状态，不触发远端提交 |
| `DELETE /api/reviews/{id}` | 委托 `TaskItem action-delete`，把复核行标记为删除 |
| `POST /api/reviews/delete` | 批量委托 `TaskItem action-delete`，语义同上 |

固定护栏：

- `confirm` 不等于 `submit`，不得把 `remote_state` 改成 `success`。
- `delete` 不删除源媒体，也不删除源 `TaskItem`。
- `delete` 只把当前复核层对象或待提交差异集合标记为 `删除`。
- 新增前端和测试优先使用 `/api/task-items/*`，仅旧 Review 壳允许继续调用 compat。

## 12. 数据模型补充建议

`task.py` 现有模型基本够用，建议补以下字段：

| 字段 | 用途 | 优先级 |
|---|---|---|
| `task.last_pull_end_at` (datetime) | 滚动窗口的上界游标，下次拉取的起点 | **必需** |
| `task.last_run_started_at` (datetime) | 上一次执行的发起时间 | 推荐 |
| `task.skipped_count` (int) | 累计跳过的重复条数 | 推荐 |
| `task.model_id` (int, FK) | 关联 `multimodal_model.id`，否则只能用全局默认 | 推荐 |
| `task_item` 唯一索引 `(task_id, file_fid)` | 防止重复拉取的硬约束 | **必需** |
| `task_item.llm_raw_json` (text) | 保存 LLM 原始响应，便于排错 | 可选 |

---

## 13. 异常与重试

| 场景 | 策略 |
|---|---|
| 上游接口 5xx / 超时 | 指数退避重试 3 次 |
| token 失效 | 已由 `client_auth` 自动处理 |
| 文件下载失败 | 单 item 标记 fail，不阻断 task |
| LLM 调用失败 | 单 item 标记 fail，不阻断 task |
| LLM 返回非法 JSON | 重试一次 + 强化 prompt；仍失败标记 fail |
| 提交远端失败 | 训练目录仍保存；下次手动重提 |
| 调度器重启 | 启动时扫僵尸任务 + 重新注册 active job |

## 14. 开发顺序建议

1. `services/upstream_api.py`：先封装好 3 个上游接口的同步调用（沿用现有 `client_auth`）
2. `services/task.py` + `api/task.py`：CRUD + filter 序列化（不含执行）
3. `services/task_steps/fetch.py` + `download.py` + `detail.py`：跑通前 3 步（不依赖 LLM）
4. `services/task_steps/matcher.py`：先做图片 IoU 匹配（视频可后做）
5. `services/task_steps/llm.py` 图片分支
6. `services/task_steps/uploader.py`
7. `services/task_runner.py`：串联整条链
8. `services/task_scheduler.py`：接入 APScheduler
9. 视频抽帧 + track_id 分组（独立模块，最复杂）
10. 前端页面：任务列表 / 详情 / TaskItem 列表 / 人工确认面板

每一步都先 `Test.md` → 测试用例 → 实现，遵循项目 TDD 规范。
